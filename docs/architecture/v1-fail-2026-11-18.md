## 2. The invariant, restated, and every consumer
**I-main (unchanged in intent).** After `MAIN_PR_BASELINE`, no workflow token (`GITHUB_TOKEN` of any run, on any
branch) can move `main` to a commit that changes code. Code here means anything a later run executes or publishes
under a credential. Every such commit reaches `main` only as a person's merge of one PR, reviewed at its head.
**What the 2026-11-18 evidence shows:** with data on `main` and merged by a bot, this needs a path-aware merge rule
that the bot can't satisfy for code and can satisfy for data. On this repository (public, user-owned, GitHub Free),
GitHub offers no such rule that we can verify (section 3). So the recommended form is:

**I-main''.** `main` moves only by a person's bypass merge of a reviewed PR. No workflow token can satisfy `main`'s
merge rule for any PR. `main` tracks no `data/`. Curated inputs (the roster, procedural titles, the corrections log)
are reviewed code under `config/`. Collector output lives on branch `records-data`, which only moves forward.
**I-data''.** `D`'s tree meets the narrowed `SHAPE''` (regular `*.json` and `changes.jsonl` under `data/`, no `.yml`)
and holds none of the curated names.
**I-prov (new).** The gate accepts `D` only if one of two holds. (a) Its tree listing (`git ls-tree -r -z D -- data`,
written to a file) carries an artifact attestation signed by `.github/workflows/daily-update.yml` at
`refs/heads/main` in this repository, on a GitHub-hosted runner, with predicate type SLSA provenance v1. Only J2
holds `attestations: write`; `deploy` holds `id-token: write` too, so the certificate alone can't tell the jobs
apart. (b) `D` is the seed commit (the parentless root of `records-data`) and its digest equals
`RECORDS_DATA_SEED_DIGEST`, pinned in the gate by the reviewed cutover PR. Because the attestation is on the tree, a person's rollback that
restores an earlier attested tree whole is accepted. A hand edit isn't.
**I-run''.** A credentialed run uses exactly two commits, both fixed by the gate: code `S = github.sha` on `main`,
checked against I-main''; and data `D` = the `records-data` head read once, checked against I-data'' and I-prov.
No input selects another `D`. Data is only ever read as data.
**I-pub (new, content tripwire).** A run deploys only if no vote, roll call or outcome already on the live site
changes or disappears. "Live" means the `D` recorded in the site's own `build-info.json`. The exceptions are
changes listed in the reviewed `config/published-fact-changes.yml`; `allow_shrink` never counts. Otherwise the run opens an issue and holds the
deploy. The data push still happens, so nothing is lost.

## 3. Options (question 2)
- **A. Required approvals 1 (or more) with code-owner review, data still on `main`.** Not reachable. The approval
  count applies to every PR into `main`, because a branch ruleset's PR rule has no path condition (GitHub: "require
  that all pull requests receive a specific number of approving reviews"). The data PR is authored by
  github-actions[bot], which can't approve its own PR, and the only other writer is gn0sh. Making it mergeable
  needs a second automated identity: a new token or App, which is hard stop 5 and was already rejected in ADR 0010.
  Medium-high confidence.
- **B. Path-restricting push rule** (block changes outside `data/` for non-bypass actors, `data/**` as the allowed
  exception). This would be the ideal native fix, but push rules are documented for private repositories on
  Team plans and internal repositories on Enterprise. This repository is public, on Free and user-owned. Not
  available (medium-high confidence, from GitHub's docs and changelog).
- **C. Required status check, required deployment, or a fine-grained token.** Forgeable by the same actor, or a new
  secret (ADR 0010, unchanged).
- **D. "Don't build it": accept T7 as a residual.** Keep R2 on, approvals 0 and the gate, and drop V1' as a
  precondition of the note. Steelman: T7 needs a writer, and writers already hold admin. Two FAILs show each
  GitHub-native guess costs a day and a live canary. Against: I-run then breaks silently for one run, because a
  bot-merged workflow on `main` can declare `environment: morning-note` before the gate sees it. That is the exact
  case the note's key depends on. The only remaining control is E2's required reviewer, which means a daily click
  for Brian. Judgment, medium.
- **E. Data off `main` (ADR 0010's fallback), as section 2.** **Chosen** (Brain Trust Fix First, 5-1, gated on
  U3; ADR 0011). It's the only option that holds I-main with what this repo has. It doesn't depend on unverified
  GitHub behaviour (code owners at 0, rename paths, author exemptions), only on two well-documented behaviours: an
  author can't approve their own PR, and a ruleset refuses a merge below the approval count. Bypass via the API (U3)
  is the one load-bearing unknown, and it's tested first. Cost with the Brain Trust changes: about 3-4 days plus
  security review. Reversible by script (S4 abort and the cutover rollback in the task list). It's still hard to
  reverse in practice once baselines and history depend on two branches.
- **Fallback if U3 fails:** B plus a separate sender repository (Budget Hawk's steelman). The site stays
  bot-deployable via T7, which is why it lost.

**Risks of E:** (1) U3 false: then every team merge needs Brian's "bypass rules" click, which would sink the team's
throughput. That's why it's probed first, before any rework. (2) Two-commit pinning: closed by the gate reading `D`
once, with no `data_sha` input. (3) `records-data` stays writable by any write-token workflow (M-2). I-prov refuses
an unattested tree, and I-pub catches an attested old tree or a hostile-PDF change to published facts. Residual:
attested new facts that are wrong but add nothing already published. (4) "Exactly two writers, R2 off" is
load-bearing for R1''; S1 checks both on every run of protect-main. (5) Cutover day: the Operator's traps (gate on
a missing `data/` tree, seed racing 09:07, a stale branch merging `data/` back, cache order in J1). They're handled
by the scripted cutover, the I-main'' refusal of tracked `data/`, and J1's step order. The branch can't be named
`data` while `data/*` branches exist (git ref conflict), hence `records-data`. (6) Local and PR preflight need
`fetch-data`, which ships in the cutover PR. (7) Every merge is a bypass, so the bypass log no longer flags
anything (Skeptic). The gate's person-merge check and S2's printed rule-suite result take over that role. (8)
Attestations go to the public Sigstore transparency log. That's fine: the data is public. (9) Replay and settings
drift (PR #54 findings 7 and most serious): a write-token workflow can push an earlier attested tree; it's accepted
(the rollback path needs it) and I-pub catches it only if it drops or changes a published fact. R1'' rests on
settings no run reads; `protect-main` from Brian's PC after any settings change and before `MAIN_PR_BASELINE` is the
only check. **U3-0 = no** (proxy 403 on the no-op ruleset PUT, 17:37 UTC 2026-11-18), so every ruleset, R2 and
environment write is Brian's.

## 4. What the next probes must show
**U3 positive control first**, before any rework: `docs/ops/u3-positive-control.md`. It's a live, scripted,
reversible toggle of `main`'s approval count, with a team merge of one docs PR in the window. PASS = that merge's
rule suite reads **suite `bypass`, `pull_request` `fail`**, with `merged_by` gn0sh. Anything else stops E.
**V1'' probe** after the cutover (R1'' live, R2 off, S3 rewritten):
1. Targets W (workflow file), N (`sitegen/` file) and D0 (a `data/` file into `main`, now also refused). Each is
   opened by gn0sh **and**, as a second set, by the runner's `GITHUB_TOKEN`. That `POST pulls` must be refused while
   R2 is off; record the refusal.
2. For each target: the bot APPROVE is refused (R2 off), and REST squash and GraphQL squash are refused with a
   message naming required approving reviews. The runner records every target. A merge still ends the run, but it
   prints `NOT-TRIED` for each target it skipped, so a FAIL stays complete.
3. A direct push to `main` by `GITHUB_TOKEN` is refused.
4. A workflow dispatched on a scratch branch is refused both environments (Opponent). So is a run at a probe tag
   ref (`v1pp-probe`, PR #54 finding 2), and creating a tag named `main` is refused by R-T.
5. A push of an unattested tree to a scratch copy of `records-data` is refused by the gate. Run it as a gate unit
   test on a fixture repo, not on the live branch.
6. `main` is unchanged, and every probe PR is closed unmerged.
7. After the cutover: the first scheduled run fast-forwards `records-data`, attests it, and deploys, and the site's
   `build-info.json` shows the new `D`. `main` isn't touched by the run, and its rule suites list no
   github-actions[bot] entry.
H1 is dropped: no CODEOWNERS dependency remains.
