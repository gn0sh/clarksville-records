## 2. The invariant, restated, and every consumer
**I-main (unchanged in intent).** After `MAIN_PR_BASELINE`, no workflow token (`GITHUB_TOKEN` of any run, on any
branch) can move `main` to a commit that changes code. Code here means anything a later run executes or publishes
under a credential. Every such commit reaches `main` only as a person's merge of one PR, reviewed at its head.
**What the 2026-11-18 evidence shows:** with data on `main` and merged by a bot, this needs a path-aware merge rule
that the bot can't satisfy for code and can satisfy for data. On this repository (public, user-owned, GitHub Free),
GitHub offers no such rule that we can verify (section 3). So the recommended form is:

**I-main''.** `main` moves only by a person's bypass merge of a reviewed PR. No workflow token can satisfy `main`'s
merge rule for any PR. Data lives on branch `records-data`, which only moves forward, and whose tree meets I-data.
**I-run''.** A credentialed run uses exactly two commits, both fixed by the gate: code `S = github.sha` on `main`,
checked against I-main'', and data `D` on `records-data`, checked against I-data. Data is only ever read as data.

## 3. Options (question 2)
- **A. Required approvals 1 (or more) with code-owner review, data still on `main`.** Not reachable. The approval
  count applies to every PR into `main`, because a branch ruleset's PR rule has no path condition (GitHub: "require
  that all pull requests receive a specific number of approving reviews"). The data PR is authored by
  github-actions[bot], which can't approve its own PR, and the only other writer is gn0sh. Making it mergeable
  needs a second automated identity: a new token or App, which is hard stop 5 and was already rejected in ADR 0010.
  Medium-high confidence.
- **B. Path-restricting push rule** (block changes outside `data/` for non-bypass actors, `data/**` as the allowed
  exception). This would be the ideal native fix, but push rules are documented for private repositories on
  Team plans and internal repositories on Enterprise. This repository is public, on Free and user-owned. Not
  available (medium-high confidence, from GitHub's docs and changelog).
- **C. Required status check, required deployment, or a fine-grained token.** Forgeable by the same actor, or a new
  secret (ADR 0010, unchanged).
- **D. "Don't build it": accept T7 as a residual.** Keep R2 on, approvals 0 and the gate, and drop V1' as a
  precondition of the note. Steelman: T7 needs a writer, and writers already hold admin. Two FAILs show each
  GitHub-native guess costs a day and a live canary. Against: I-run then breaks silently for one run, because a
  bot-merged workflow on `main` can declare `environment: morning-note` before the gate sees it. That is the exact
  case the note's key depends on. The only remaining control is E2's required reviewer, which means a daily click
  for Brian. Judgment, medium.
- **E. Data off `main` (ADR 0010's fallback), as section 2.** **Recommended.** It's the only option that holds I-main
  with what this repo has. It doesn't depend on unverified GitHub behaviour (code owners at 0, rename paths, author
  exemptions), only on two well-documented behaviours: an author can't approve their own PR, and a ruleset refuses a
  merge below the approval count. Bypass via the API (U3) is the one load-bearing unknown, and it's cheap to test.
  Cost: one workflow rework plus a cutover, about 2-3 devops/backend days plus security review, as ADR 0010 estimated.
  Reversible: merge `records-data` back and restore R1 json. But it changes the data model and every reader, so
  **a Brain Trust is required first**, as ADR 0010 says. It's hard to reverse in practice once rollback runs,
  baselines and history depend on two branches.

**Risks of E:** (1) U3 false: then every team merge needs Brian's "bypass rules" click, which would sink the team's
throughput. Probe it first: it's the cheapest check, and it can run before any rework. (2) Two-commit pinning: if
D isn't fixed by the gate, a run could build and publish data the gate didn't check. (3) `records-data` stays
writable by any write-token workflow (M-2, unchanged): bad data, never code. The neutrality of a public records
site rests on I-data and review of the collector, as today. (4) Cutover day: J2 and J1 must switch in the same PR as
the seed of `records-data`. A branch can't be named `data` while `data/*` branches exist (git ref conflict), hence
the name `records-data`. (5) Local and PR preflight break until `fetch-data` lands; ship it in the cutover PR. (6)
Repository size: `data/` (45 MB working tree) is duplicated in history once at the seed. Harmless.

2. Targets W (workflow file), N (`sitegen/` file) and D0 (data-only into `main`, which must now also be refused).

   refused while R2 is off; record the refusal.
3. For each target: the bot APPROVE is refused (R2 off), and REST squash and GraphQL squash are refused with a

   prints `NOT-TRIED` for each target it skipped, so a FAIL stays complete.
4. A direct push to `main` by `GITHUB_TOKEN` is refused.
5. `main` is unchanged, and every probe PR is closed unmerged.
6. After the cutover: the first scheduled run fast-forwards `records-data` and deploys, and the site shows the new
   date. `main` isn't touched by the run, and its rule suites list no github-actions[bot] entry.
